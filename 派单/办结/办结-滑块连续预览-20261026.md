# 交接：滑块拖动连续预览（第 4 期）

> 对应 HANDOFF「新指令」第 4 期（交办 2026-10-26 21:45）——用户实测 bug：按住滑条拖动翻页，只有起点一张和落点一张，中间图全不显示。
> 代码提交 `83ab10e`（6 files, +144/-2）· 探针 `Temp/fifo-test/`（Temp 在 .gitignore，脚本不入库）

---

## 一、根因

`Chrome.cpp` `ControlBar::mouseReleaseEvent` 原注释：「整段拖动只在这里发一次：松手才真正跳图（拖动中只动视觉）」。拖动中 `applyPageFromX()` 只更新 `m_page` 与页码绘制，**不发任何跳图请求**；松手才 emit 一次 `pageRequested`。所以拖动路径上只有起点（上一次跳转留下的画面）和落点。

---

## 二、实现（三处，互不影响既有通道）

### 1. `Chrome.h/.cpp`：拖动源发节流预览信号

- 新增信号 `void pagePreviewRequested(int index);`（1-based）。
- `applyPageFromX()` 页码变化且 `m_dragging` 时，按 ≥60ms 节流 emit：

```cpp
if (m_dragging && (!m_previewClock.isValid() || m_previewClock.elapsed() >= 60)) {
    m_previewClock.restart();
    emit pagePreviewRequested(m_page);
}
```

- 滑杆 mousePress 分支 `m_previewClock.invalidate()`：本次拖动第一次换页立即出帧，不等 60ms。
- 松手 `pageRequested` 一字未动；键盘步进同样不变。显式跳转路径完全保留。

### 2. `ImageCache`：独立拖动预览通道

- 新接口 `requestDragPreview(const QString &path, const QSize &size)` + 信号 `dragPreviewReady(path, image)` + 私有 `startDragDecode()`。
- 独立缓存 `m_dragCache`（64MB，按字节成本）：**缩放图不能混进 `m_fullCache`**，否则落点会停成模糊帧。
- 命中顺序：全图缓存 → 拖动预览缓存（两者都 0ms 直发，不排队）→ 未命中才入 `m_dragPending` 并串行解码。
- 单飞：`m_dragInFlight` 同一时刻只有 1 个；`startDragDecode()` 在每次解完后重入，落点变过就接着解最新那张。
- 快帧：沿用 `QImageReader::setScaledSize`（`previewSize` 量级 10~30ms）。
- 与 `requestFull` 对齐：`requestFull()` 顶部若命中 `m_dragInFlight` → `m_dragPromote = true`，解完按**快帧**上屏（`fullReady(path, img, true)`），防止同页双解码导致回跳；同时 `m_dragMuted = true` 并清 `m_dragPending`，旧落点的在飞结果只入缓存。
- `cancelPending()` 清 `m_dragPending` + 置 `m_dragMuted`；`clearFull()` 复位全部拖动状态（含作废在飞结果）。

### 3. `MainWindow`：跟手上屏 + 拖动中停预读

- `pagePreviewRequested` → 校验索引 → `m_preloadTimer->stop()` → `m_cache->requestDragPreview(...)`。
- `onDragPreviewReady`：`animatable()` 时先 `stopAnimation()`（否则旧 GIF 的 tick 会把画布刷回上一帧），再 `showImage(image, path, true)`。
- **不碰 `m_dir` 索引、不写元数据、不改 `m_currentPath`**；松手仍由 `pageRequested → jumpTo` 走一次全图跳转。

## 三、与交办单字面的一处差异（口径要认这个）

单子写「滑块位置变了 → 在飞旧结果到达只入缓存不上屏」。**按字面实现会直接复现「只出两张」**：60ms 节流 + 约 70ms 解码，`m_dragPending` 永远非空，于是每一帧都判 stale，全部只入缓存——用户看到的还是起点 + 落点。

最终口径：

```
拖动中解完的每一张都按序 emit dragPreviewReady（解码串行，顺序天然与拖动方向一致）
只有「真实请求介入」（松手 jumpTo / 连按，即 m_dragMuted）后，拖动结果才只入缓存不上屏
```

latest-wins 保留在「意图」层面（`m_dragPending` 只记最新落点，中间的旧意图不补解），而不是「丢弃已解完的帧」。这样既跟手又不越序。

## 四、实测（探针：鼠标注入 + 窗口标题轮询 + PrintWindow）

样本：`Temp/fifo-test/big`（2000×1500 大图 12 张）。

| 场景 | 命令要点 | 结果 |
|---|---|---|
| 慢拖 700ms 跨 12 页 | `probe_drag_slider.py <dir> 12 0.06` | 右拖 `1,2,4,5,6,7,8,10,11,12`；回拖 `12,11,10,9,8,6,4,3,2,1`；终帧 12/1 正确，双向单调不回跳 → PASS |
| 逐格慢拖延迟 | 同上 C 段 | `{2:5,3:8,4:11,5:13,6:11,7:7,8:10,9:11,10:29,11:17,12:4}` ms，**经过过的 10/10 <40ms** → PASS |
| 快甩 300ms（15×20ms） | `probe_drag_slider.py <dir> 15 0.02` | A `1,2,4,6,9,12`（6 帧，非「只出两张」）；B `12,11,9,8,7,5,4,2,1`；终帧正确、单调；C 8/8 <40ms → PASS |
| 落点全图 | `probe_full_image.py` | 两路都停「适合窗口」档：拉普拉斯方差 7773.6（直接开 img12） vs 7669.1（拖到 12 松手），**方差比 0.987** → 是完整图不是缩放预览，PASS |
| 回归 连按 | `probe_fifo10.py` | 1→11 严格递增，中间帧 9/9，回翻 34ms → PASS |
| 回归 空闲预读 | `probe_preload.py` | 命中 26/29/26ms vs 未预读 71/61/65ms → PASS |
| Esc 取消回弹 | 代码核对 | `ControlBar` 的 `Qt::Key_Escape → clearFocus()` 未改动，拖动中取消回弹视觉保留 |

探针判定细节：

- 中间帧「零跳空」只对**物理上经过过**的格子断言（逐格慢拖段）；快甩允许物理跳帧，但断言帧数下限（>2）与终帧正确、序列单调。
- `probe_drag_slider.py` 的可选参数：`argv[2]=steps`、`argv[3]=sleep`；`steps <= 15` 视为快甩，帧数下限降为 3。
- 清晰度探针用 `PrintWindow(hwnd, hdc, 2)` 抓窗口自身位图，避免 `ImageGrab` 抓到被遮挡的其他窗口。

**调试过程中踩到的两个坑（别再踩）**：

1. `m_dragCache` 最初 32MB——12 张视口级预览合计超过上限，回拖命中率掉到 57~58ms（LRU 已淘汰）。改 64MB 后回拖全部 <40ms。
2. 拖动预览「落点已变就丢」会让连续拖动永远不出帧（见 §三）。

## 一、翻页调度 FIFO

### 现场判定

下单时以为「FIFO 完全没做」，实际是**主体早在 `d89a2e2` 已落地**（`perf(cache): 翻页 FIFO 逐张播放 + 快帧预读 + 缓存按字节成本`），
只是后面几轮没人回传实测数据，看起来像悬空。逐条对单：

| 单子要求 | 状态 | 证据 |
|---|---|---|
| 1. 全解码入口收敛单一 FIFO、队首单飞、显式跳转清队 | 已实现（`d89a2e2`） | `ImageCache::m_queue` + `startNext()`；`jumpTo()` 先 `cancelPending()`；顺序翻页 `onNext/onPrev/±10` 走 `loadAsync()` 入队，不走 `jumpTo` |
| 2. 队列上限 8，满丢最老 | 已实现（`d89a2e2`） | `requestFull()` 里 `while (m_queue.size() > 8)` 丢「尚未开始解码」的最旧项，在飞队首不动 |
| 3. 空闲预读：队列空 + 300ms 无输入 → 前后各 1 张 | **本轮补上**（`f196251`） | `MainWindow::m_preloadTimer`(300ms singleShot，每次 `loadAsync` 重启) + `MainWindow::preloadNeighbors()` + `ImageCache::preload()/isIdle()/startNextPreload()` |
| 4. `onFullReady` 过期守卫不再丢结果 | 已实现（`d89a2e2`），但**方式与单子字面不同** | `MainWindow::onFullReady` 已无守卫，只调 `showImage()`；结果先 `insertFull()` 入缓存，再按 FIFO 顺序上屏 |

### 关于要求 4 的实现方式（重要，别按字面改回去）

单子写的是「不是当前页就回写缓存但**不发信号**」。按字面实现会立刻退回下单时的 bug：
连按 7 次时，第 1 张解完时 `m_currentPath` 早已是第 7 张，于是 1~6 全部被判「不是当前页」→ 不上屏 → 又变回「只出最后一张」。

现在的口径是：
- **用户请求的帧**：FIFO 保证 emit 顺序 == `requestFull` 调用顺序，所以每一帧当时就是「该显示的那一帧」，逐张上屏；结果始终先入缓存，缓存成本按字节计，不会再出现「预热了却留不下」。
- **空闲预读的帧**：本来就不该上屏（上了就是画面乱跳），走独立预读通道，只 `insertFull()` 不发信号 —— 这正是要求 4 想表达的「结果别扔，预热成果要留」。
- 预读中的那一页若被用户真的要（`requestFull` 命中 `m_preloadPath`）→ 标记 `m_preloadPromote`，解完直接按序发出，不另起任务。这样避免「同一页两个解码、后一页先到、画面回跳」。
- 预读与全图解码共用「单飞」：预读在飞时，新请求只排队不放行，等预读结束再按序走，保证不越序。

## 一、P0 真 bug：键盘「操作」列改绑后无效（还会把原键弄丢）

### 现象

设置 → 键盘 → 把某行的「操作」改成别的动作 → 保存 → 该键位**不执行新动作**，而且原动作的键也失效。

### 根因（已定位到行）

`src/MainWindow.cpp` `applyShortcutConfig()`（约 1294-1330 行）：

```cpp
for (const SlotDef &d : shortcutSlotDefs()) {
    ...
    const QString target = cfg.actionBinding(slot, slot);
    QAction *dst = m_actions.value(target);
    ...
    dst->setShortcuts({ seq });          // ← 替换语义
}
```

两个槽位可能指向**同一个目标动作**，而 `setShortcuts` 是替换不是追加，后遍历的槽位把先前写入的键覆盖掉。槽位表顺序（`shortcutSlotDefs()`）里 `openfolder` 排在 `open` 之后，所以：

1. `open` 行改绑到 `openfolder`、键 `Ctrl+O` → 给 openfolder 动作 `setShortcuts({Ctrl+O})`
2. `openfolder` 行自己的键 `F` 等于出厂值 → 走默认分支 `setShortcuts({F})` → **把 Ctrl+O 覆盖掉**
3. 净效果：Ctrl+O 什么都不做（open 动作已被清空且不再是任何槽位的目标），F 照旧。**用户改了个寂寞。**

### 修法（按目标动作聚合，别逐槽替换）

`applyShortcutConfig()` 改成两趟：

```cpp
QHash<QString, QList<QKeySequence>> perAction;          // 目标动作 → 键列表
for (const SlotDef &d : shortcutSlotDefs()) {
    const QString slot = QString::fromLatin1(d.slot);
    if (!cfg.actionEnabled(slot, true)) continue;
    const QString target = cfg.actionBinding(slot, slot);
    if (!m_actions.contains(target)) continue;
    const QString stored = cfg.actionKey(slot);
    const QKeySequence seq = QKeySequence::fromString(stored, QKeySequence::PortableText);
    if (target == slot && (stored.isEmpty() || seq == d.defaults.value(0))) {
        for (const auto &k : d.defaults)
            if (!perAction[target].contains(k)) perAction[target].append(k);
        continue;
    }
    if (!seq.isEmpty() && !perAction[target].contains(seq))
        perAction[target].append(seq);
}
// 先清空全部槽位动作（沿用现有第一趟循环），再统一安装
for (auto it = perAction.constBegin(); it != perAction.constEnd(); ++it)
    m_actions.value(it.key())->setShortcuts(it.value());
```

要求：

- 去重（同一动作收到同一键两次不能装两遍，Qt 会报警告）。
- 覆盖场景：**两个槽位绑同一动作**（如 open + openfolder 都指 openfolder）时，两个键都要装到该动作上。
- 不改 `shortcutSlotDefs()` 的键位定义。
- 改完顺手检查 `factoryShortcutLists()` / 冲突检测是否受影响（它按槽位读出厂表，不需要动；但「两个槽位同目标」时冲突检测不应误报同键冲突）。

### 验收（必须实测，不许只看代码）

1. **默认态回归**：干净配置启动，14 个动作键位与出厂一致（`--smoke "report"` 的 `keys=` 字段核对）。
2. **改绑生效**：把「打开」行的操作改为「打开文件夹」保存 → **Ctrl+O 和 F 都能打开文件夹**（两个键都要验，这是本次 bug 的核心）。
3. **改回**：把「打开」行操作改回「打开」，Ctrl+O 恢复打开文件、F2 仍在。
4. **禁用槽位**：把「打开」行取消勾选保存 → Ctrl+O 无任何动作；重新勾选恢复。
5. **冲突仍拦**：把「打开」键改成 `Ctrl+P`（打印占用）→ 保存被拒、行高亮、config 不落盘。
6. `--smoke "next10,report"` 退出正常、翻页正常。

## 三、P1 非 bug：背景颜色/边框颜色「改了没用」——实测是生效的

### 监工实测（可复现）

把 `build/config.ini` 改成 `view/bkgnd_color=#FF0000`、`view/border_color=#00FF00`，用自渲染截图（`--screenshot`）抓 720×500 窗口：

- 纯红 `#FF0000` 占 **76.70%**（四角全部命中）
- 纯绿 `#00FF00` 占 **0.67%** = 2×(720+500)−4 = 2436px ÷ 360000 ≈ **正好 1px 边框**

结论：`ImageCanvas::setBackgroundColor()`（brush + stylesheet 双写）与 `setBorderColor()`（paintEvent 1px 内沿）都正常工作，保存后 `onSettings() → applyRuntimeSettings()` 也会立即重刷。

### 用户的"没用"是三个感知因素叠加

1. **选的就是默认值**：设置页默认背景 `#202020`、边框 `#000000`；用户选的正是这两个值，等于没改。
2. **边框只有 1px**，`#000000` 在深色界面上肉眼几乎不可见。
3. **图片适应窗口时背景被图占满**，设置页里改背景色根本没有可见区域。

### 建议（可选，做不做都行）

- 两个颜色按钮旁加小字标注「默认」，当前值等于默认时按钮文字加「（默认）」后缀。
- 颜色按钮 tooltip：「背景色在图片未铺满窗口时可见；边框为 1px 描边」。
- 不改逻辑，只加说明——本次不作为返工门槛。

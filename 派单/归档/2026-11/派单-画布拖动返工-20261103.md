## 二、Bug：缩放越小越拖不动，约 0.1× 时完全失效

实测（同一张 4000×3000 图）：

| 缩放状态 | 拖动 -900,-600 的实际位移 |
|---|---|
| fit（约 0.29×） | 正常，1:1 |
| 约 0.23×（滚轮下 1 档） | 横向 -262（含夹持），**纵向仅 -8** —— 纵向行程几乎耗尽 |
| 约 0.1×（滚轮下 5 档） | **(+9.6, -5.2) ≈ 不动**；再反向拖 +1400,+900 → **位移 (0,0)** |

进程不崩、画面不错乱，就是拖不动。

## 三、根因（监工侧分析，已与实现核对）

`updateSceneRect()`（`ImageCanvas.cpp:579`）把 padding 写成**场景坐标**：

```cpp
const qreal px = viewport()->width()  * 2.0;   // 场景单位
const qreal py = viewport()->height() * 2.0;
```

而滚动行程 = `sceneRect × zoom − viewport`。**padding 存在场景里，会被 zoom 同比例缩小**：

- zoom 0.29 时：pad×zoom ≈ 0.58×viewport，行程尚可；
- zoom 0.23 时：纵向 (3000+4×883)×0.234 ≈ 1528 物理，减视口 1104，单边只剩 ~210；实际纵向几乎为 0（还有第二处问题，见下）；
- zoom 0.1 时：(4000+4×1638)×0.096 ≈ 1014 物理 < 视口 2048 → **行程归零**。

一句话：**padding 必须与 zoom 无关，否则缩小就失效**。这正是当初单子 3.1 里「2 倍视口」没有写清单位导致的——按物理视口给，不该按场景单位给。

附带核对：单子 3.2 要求的归一化坐标改造——`viewCenterNormalized()` 已按图片矩形为基准（达标）；`keepScenePointAt()` 已改为按滚动条 range 判断（达标）。

## 四、修法

### 4.1 padding 除以当前 zoom（核心，一个函数）

```cpp
void ImageCanvas::updateSceneRect()
{
    if (!m_item) { scene()->setSceneRect(QRectF()); return; }
    const QRectF img = m_item->boundingRect();
    const qreal z = qBound(0.05, transform().m11(), 1.0);
    const qreal px = viewport()->width()  * 2.0 / z;
    const qreal py = viewport()->height() * 2.0 / z;
    scene()->setSceneRect(img.adjusted(-px, -py, px, py));
}
```

这样 `pad × zoom` 恒等于 2 倍视口物理像素，任何缩放级别行程都一致。

### 4.2 每次缩放变化后都要重算

`updateSceneRect()` 目前只在 `setPixmap` / `setPixmapPreservingView` / `resizeEvent` 调用。**必须在所有 zoom 变化出口补调**：`applyZoomAt()`、`fitToWindowGeom()`、`fitToWidthGeom()`、`zoomActual()`（即 `applyZoomAt` 尾部统一调一次最稳）。

### 4.3 查纵向先行失效的第二处问题

0.23× 时纵向行程按公式还有 ~212 物理像素，实测只有 -8。修完 4.1 后如果纵向仍先于横向失效，重点查：
- `applyZoomAt` 尾部是否有 `centerOn` 把纵向拉回；
- `wheelEvent` 平滑缩放动画期间 scrollbar 值被覆盖。

## 改了什么（三处，均在 `src/ImageCanvas.cpp`）

1. **4.1 padding 除以 zoom**：`updateSceneRect()` 里 `px/py = viewport()*2.0 / z`（z 取 `transform().m11()` clamp 0.05..1.0），`pad×zoom` 恒等于 2 倍视口物理像素，任何缩放级别行程一致。
2. **4.2 缩放出口统一补调**：`applyZoomAt()` 尾部（emit zoomChanged 之后、keepScenePointAt 对齐之前——insets 收完 viewport 定型后算出的 padding 才是最终值）+ `fitToWindowGeom()` / `fitToWidthGeom()`（centerOn 前）各补一次 `updateSceneRect()`。
3. **4.3 纵向先行失效的第二处问题 = `AnchorUnderMouse`（真凶）**：不是 centerOn 也不是滚轮动画。构造里的 `setTransformationAnchor(AnchorUnderMouse)` 会在 ScrollHandDrag 滚动后按鼠标位置重映射视图，把滚动补偿吃掉。

## 4.3 证据链（400ms 滚动条定时探针 + 分帧截图，临时探针已撤）

- 修复 padding 后（AnchorUnderMouse 仍在）：0.5931× 拖动时 scrollbar value 每步 +44（与鼠标步长一致），**但画面内容 5 帧纹丝不动**——滚动量被 anchor 重映射全向吃掉。
- 监工看到的「横向 -262 含夹持、纵向仅 -8」是**全向抵消 + 行程夹持的混合表现**：横向剩部分位移、纵向被完全抵消；≈0.1× 时全向完全抵消，表现为「拖不动」。与横向纵向的行程分配无关。
- 改 `NoAnchor` 后四档拖动全部 1:1 跟手（见画布自由拖动交接单的四档位移表）。**本项目所有缩放锚点由 applyZoomAt/keepScenePointAt 自实现，Qt 的 transformation anchor 无消费者**，改 NoAnchor 无副作用；滚轮缩放（wheelEvent→applyZoomAt）与显式 100%/fit 的锚点语义不变。
